# DS2 — Review of the built Tempus landing page vs. `docs/tempus-landing-design.md`

## Verdict: REQUEST CHANGES

The build is a faithful, high-quality implementation of the spec — palette tokens, type scale, spacing, band order, component structure, copy, keyboard order, and `prefers-reduced-motion`/`prefers-color-scheme` handling all match closely and were verified against the live page, not just the code. But there is one confirmed accessibility BLOCKER (gold text fails contrast on light backgrounds in several places) and two confirmed HIGH content bugs (the Apple Watch feature image and the OG share image are both cropped wrong), so this isn't ready to ship as-is. Everything below was checked live in the browser (computed styles, live DOM, actual network requests, keyboard tabbing, contrast math run against the rendered colors), not just read from source.

## Findings

| # | Severity | Where | What I saw | Fix |
|---|---|---|---|---|
| 1 | **BLOCKER** | `assets/css/tempus.css:3` `.eyebrow{color:var(--gold-500)}`; `:4` `.text-link{color:var(--gold-500)!important}`; `:8` `.faq-contact a{color:var(--gold-500)}` | Gold-on-light-band text fails WCAG AA. Measured on the live page: `#c8862e` on the light `--bg` `#fdfbf8` = **2.94:1** (needs 4.5:1 for normal text, spec §1.1 and the ui-ux-pro-max `color-contrast` gate). Confirmed live instances: the "WHY TEMPUS" eyebrow, the "Read the full privacy policy →" link, and the FAQ's "viktor@gamov.io" / "full support page" links. Root cause: `--gold-500` was only ever verified against the ink band in spec §1.1's contrast table (6.07:1 there — fine) — the light-band pairing was never checked, in the spec or the build. | Add a light-band gold text token (e.g. `--gold-600` `#9c6420`, already defined for CTA-pressed — verified **4.80:1** on `#fdfbf8`) and apply it via `.section:not(.ink-band) .eyebrow`, `.section:not(.ink-band) .text-link`, and `.faq-contact a` (drop the `!important` on `.text-link` so a more specific light-band rule can win). Leave the ink-band gold (`.features .eyebrow`, footer links) as-is — those measured 6.07–9.20:1 and are fine. |
| 2 | **HIGH** | `static/tempus/hero/00c_watch_hero-1x.webp` / `-2x.webp`; hardcoded `width="1320" height="2868"` at `layouts/tempus/list.html:146` | The Apple Watch feature image ("Time on your wrist") is cropped wrong. The source composite is 1536×2752, but the delivered webp was resized to 1320×2868 — the *phone* hero's canvas, not its own aspect ratio. The page's `.watch-crop` CSS (`assets/css/tempus.css:7`, `aspect-ratio:1536/2035; object-fit:cover; object-position:bottom` — this part is correct, matches spec §3 exactly) then crops *that* mis-shaped image, and because the wrong-aspect source is so much taller-per-width than intended, ~85% of the vertical extent gets cropped from the top before the container even sees it — the sunset skyline is almost entirely gone, leaving a small, low-context watch-on-wrist thumbnail. This contradicts the image's own alt text ("against a city skyline at dusk") and spec §3 Row D's intended composition (skyline + wrist + watch). Visible in `desktop-1440-light-full.png`, row D. | Regenerate `00c_watch_hero-1x.webp`/`-2x.webp` from the original 1536×2752 PNG, preserving its native aspect ratio (bottom ~74% crop, ≈1536:2035) instead of reusing the phone-screenshot resize pipeline. Fix the hardcoded `width`/`height` on `layouts/tempus/list.html:146` to match. |
| 3 | **HIGH** | `static/images/og/tempus-landing.png` | Correct 1200×630 dimensions, but the crop itself is wrong: it's an extreme, off-center zoom into the *bottom* of one phone screenshot (just the "San Francisco" row and the time-scrubber control against mostly blank white space) — not "phone + globe centered, headline band excluded" as spec §5 asks for. As a link-preview thumbnail (Slack, iMessage, Twitter/X card) this will look like a broken/random screenshot fragment, not a recognizable app hero. | Recrop centered on the phone + globe artwork from `00b_clock_list_hero`, matching the same art-only framing already used correctly for the on-page hero. |
| 4 | MEDIUM | `assets/css/tempus.css`, both `@media(max-width:800px)` breakpoints | The only breakpoint below desktop is 800px. The review brief's tablet reference viewport (834×1112 — a standard iPad Air/Pro portrait width) is *above* that, so at 834px the page still renders the desktop two-column hero and zig-zag feature rows instead of the stacked tablet layout spec §2 calls for ("Tablet: stacked... image max-width 360px"; "tablet/mobile always image-above-text"). Confirmed in `tablet-834-light-full.png` — hero and all four feature rows are side-by-side, not stacked. Real iPads at 834–1024px wide never get the intended tablet treatment; only phones ≤800px do. It's not broken (no overflow, text still reads fine), just not the layout the spec specified for this breakpoint. | Raise the stacking breakpoint to ~860–900px, or add a dedicated tablet breakpoint, so 834px-wide viewports get the stacked treatment. |
| 5 | MEDIUM | `assets/css/tempus.css:6` `.value-grid p,.privacy-promise p,.faq p{color:var(--text-secondary)}` vs. `:3` `.eyebrow{color:var(--gold-500)}` | CSS specificity collision: both rules match a `<p class="eyebrow">` inside `.privacy-promise`/`.faq`, and the compound selector (`.privacy-promise p`, specificity 0,1,1) beats the single class selector (`.eyebrow`, 0,1,0). Result: the "Privacy first" and "Support" eyebrows render in plain gray body-text color, while the hero's and "Why Tempus"'s eyebrows render gold — three eyebrows on one page, two different treatments, not what spec §1.2/§2 intends (one consistent eyebrow style). Confirmed live via `document.styleSheets` rule matching. Note: this accidentally sidesteps finding #1's contrast bug for just these two instances (text-secondary is 7.1:1, fine) — fixing #1 with a properly-scoped, higher-specificity light-band override should resolve this too. | Scope the light-band gold override (from fix #1) with specificity ≥ `.privacy-promise p`/`.faq p` (e.g. `.section:not(.ink-band) .eyebrow` with an attribute or `:where()` bump, or simply reorder so eyebrow color is set after the paragraph rule), so all three light-band eyebrows render identically. |
| 6 | LOW | `assets/css/tempus.css`, `@media(max-width:430px)` `.device-shot img{border-radius:24px}` | Spec §3 says the inner screenshot radius should scale down on mobile "min 28px"; the mobile rule uses 24px. Barely perceptible, cosmetic only. | Bump to 28px if strict spec conformance matters; otherwise fine to leave. |
| 7 | LOW | `assets/css/tempus.css:3` `.tempus-page :focus-visible{outline-offset:3px}` | Spec §3's button focus-state table specifies a 2px offset; build uses 3px. Ring is clearly visible either way (confirmed in `focus-state-nav.png`). | Non-blocking; align to 2px only for strict conformance. |

## What matched the spec cleanly (verified, not assumed)

- **Palette/tokens**: every light/dark/ink/gold hex in `assets/css/tempus.css` matches spec §1.1 exactly, including the dark-mode `@media(prefers-color-scheme:dark)` override block.
- **Typography**: Lora/Inter/JetBrains Mono loaded once via the site's existing font `<link>` (no duplicate font request, confirmed via network log) — matches the "reuse the blog's font system" instruction.
- **Copy**: hero headline/subhead, all four "Why Tempus" cards, all four feature-showcase rows, the widgets/iCloud caption, the privacy-promise paragraph, and all six FAQ Q&As are byte-for-byte matches to spec §2, including the FAQ being copied verbatim from `content/pages/tempus-support.md`.
- **Hero crop**: `00b_clock_list_hero` correctly excludes the baked-in "Perfect Time, Every Time" headline band — confirmed visually and via computed `object-position`/`aspect-ratio`.
- **Screenshot device frame**: `.device-shot` (border 10px `#1a1a1a`, radius 44px outer / 34px inner, 90×26px dynamic-island pill at 12px from top) matches spec §3's component spec almost to the pixel.
- **FAQ accordion**: native `<details>`/`<summary>`, no JS, opens/closes correctly, 44px min tap target, keyboard-reachable in document order.
- **Keyboard order**: tabbed the full page — skip-link → brand → nav CTA → App Store badge → hero text link → (all four feature rows have no interactive elements, correctly) → privacy link → 6 FAQ summaries in order → footer links. Matches visual order throughout, no traps.
- **Touch targets**: nav CTA, brand link, and footer links all measured 44px tall live (a later `.brand,.nav-cta,.tempus-footer a{min-height:44px}` rule correctly overrides an earlier, tighter `.nav-cta{min-height:40px}` — verified this really does win in the cascade before ruling it out as a finding).
- **Alt text**: every image has descriptive, non-redundant alt text matching spec §2's suggested copy.
- **SEO meta**: title (48 chars) and description (154 chars) match spec §5 exactly; canonical/OG/Twitter tags all present; OG image is the right *dimensions* (1200×630) even though the crop is wrong (finding #3).
- **`/tempus/privacy/`**: unaffected by the standalone Tempus layout — still renders in the normal PaperMod site chrome (confirmed in `privacy-page-check.png`).
- **Reduced motion**: `@media(prefers-reduced-motion:reduce)` present and disables all animation/transition, as required.
